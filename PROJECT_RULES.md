# Shared project rules for Claude and students

Read README.md, docs/CONTRACTS.md, and the student's assigned task card first. The instructor must assign a task before changes begin.

1. Contribute to the existing Python/Ursina game. Do not create a replacement game.
2. Edit only the files assigned on the task card. Propose out-of-scope changes to the instructor in writing.
3. Preserve public function names, arguments, material IDs, coordinate conventions, and the save format.
4. Do not change main.py, dependencies, world bounds, or tests without instructor assignment.
5. Make one small feature at a time. Explain the plan before editing and explain the Python afterward.
6. Do not install new packages or add web services, accounts, secrets, or multiplayer for the starter tasks.
7. Provide exact test steps, expected results, and a list of changed files. Never claim a test ran when it did not.
8. Keep ground-layer blocks intact and prevent building outside the map or inside the player.
9. Use original or appropriately licensed assets and record their source in assets/README.md.
10. If an interface conflicts with another team's needs, stop that change and give the instructor a proposed contract update.

Student handoff: feature summary; changed files; tests actually run; known issues; requested shared-file changes; one explanation of code you understand.
